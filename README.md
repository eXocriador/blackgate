# blackgate

> До 2026-09-24 — `exo-ai`. Назва — рішення власника того ж дня, в тон до
> `relic` і `mikoshi`. Старий URL репо переадресовується.

Шлюз до моделей: **пули**, **драбина запасних ходів**, **облік**.

Стоїть *перед* VibeConduit, а не замість нього. Шлюз лишається виходом до
провайдерів (там живе автентифікація до Google і Vertex), blackgate бере політику,
якої в шлюзі немає взагалі: мапінгу моделей, обліку, ретраїв, лімітів і поняття
пулу в ньому нема.

    продукт ──(тир, ключ продукту)──▶ blackgate ──(id моделі)──▶ VibeConduit ──▶ провайдер

## Навіщо

2026-09-13 пул Gemini 3.x ліг цілком. Запасна модель teamself лежала **в тому
самому пулі**, що й основна, — уся драбина пішла у fail-safe за один крок.
Відповідав лише exointel, чия запасна модель випадково була з іншого пулу.

Сервіс прибирає клас хвороби, а не рядок у `.env`:

* **пул — це те, що вичерпується разом.** Не сімейство назв і не версія.
* **драбина мусить перетинати пули.** Конфіг, де сусідні сходинки в одному
  пулі, сервіс **не приймає на старті** і називає обидві сходинки.
* **здоров'я пулів — наперед.** Відомо мертвий пул драбина пропускає, а не
  з'ясовує це запитом клієнта.
* **облік.** Кожен виклик лишає рядок: продукт, модель, пул, сходинка,
  результат, латентність, токени.

## API

Продукт просить **тир**, а не модель. `fast` / `capable` / `agent` — саме те,
чим сьогодні думають exointel і teamself; id моделі стає деталлю сервісу.

```http
POST /v1/complete
Authorization: Bearer <ключ продукту>

{ "tier": "fast", "messages": [{"role":"user","content":"…"}],
  "max_tokens": 512, "temperature": 0.3, "subject": "user:42" }
```

```json
{ "content": "…", "model": "gemini-2.5-flash", "pool": "gemini-lite",
  "rung": 1, "attempts": [ … ], "totalLatencyMs": 812 }
```

`rung: 1` і масив `attempts` віддаються навмисно: продукт має бачити, що
відповіла не основна модель, — інакше деградація знову стає невидимою.

| код | що це | що робити продуктові |
|---|---|---|
| 200 | відповідь є | брати `content` |
| 429 `budget_exhausted` | добова стеля | **передати людині**, не показувати помилку і не виставляти рахунок |
| 503 `all_rungs_failed` | жодна сходинка не відповіла | fail-safe продукту |
| 400 `unknown_tier` | тиру немає в реєстрі | помилка інтеграції |

Решта: `GET /v1/pools` (стан пулів), `GET /v1/tiers` (розгорнуті драбини),
`GET /v1/usage` (скільки цей продукт спалив сьогодні), `/health/live`,
`/health/ready` (обидва без ключа; див. «Здоров'я» нижче).

Трейси: `traceparent` (W3C) у заголовку і `metadata` в тілі (`session_id`,
`trace_id`, що завгодно до 4 КБ) лягають у журнал запиту; спан OTLP стає
дочірнім до спану продукту.

Клієнти: TypeScript — `@exo/kit/ai` у [exo-kit](https://github.com/eXocriador/exo-kit);
Python — [`clients/python`](clients/python/README.md) у цьому репо (async `httpx`,
типізовані помилки на кожен рядок таблиці вище).

## Реєстр моделей — дані, не код

`catalog.yaml` монтується з теки продукту `:ro` і перечитується за mtime
(15 с). Додати модель, пул чи сходинку драбини — правка файла, **без релізу**.
Поганий реєстр на старті валить процес; поганий реєстр на перечитуванні
**відхиляється, а в роботі лишається попередній** — живий сервіс не має лягати
від того, що хтось зберіг файл посеред правки.

Розкладка пулів знята **живою пробою**, а не вгадана з імен. Проба спростувала
очевидне: `gemini-3.1-pro-low` віддавав 429, а `gemini-3.1-flash-lite` — 200.
Один префікс версії, різні пули.

**Якщо сумніваєшся — зливай пули, не розділяй.** Зайво зліплені два пули лише
звужують драбину. Помилково розділений один пул — це рівно той дефект, від
якого сервіс і написаний.

## Підроблений 200

Три моделі (`gemini-3.5-flash-low`, `gemini-3.5-flash-extra-low`,
`gemini-3-flash-agent`) виведені апстрімом з експлуатації, але шлюз віддає на
них **HTTP 200** — з `model: "model"`, `usage: null` і текстом «Gemini 3.5 Flash
is no longer available…» замість відповіді.

Наслідки без захисту тихі обидва: монітор за кодом статусу назве пул здоровим,
а продукт покаже цей текст користувачеві **як відповідь моделі**. Тому:
позначка `retired:` закриває три відомі id (сервіс не пускає їх ні в драбину,
ні в пробу пулу), а структурний детектор у `src/upstream/gateway.ts` ловить
четвертий, якого ще ніхто не бачив.

## Коди і ретраї — в одному місці

| код | ретрай | далі |
|---|---|---|
| `429` | ні | пул позначається хворим, наступна сходинка (з іншого пулу) |
| `400 INVALID_ARGUMENT` | **ні** | записати, що модель у цій формі не працює, і йти далі |
| `5xx`, таймаут | так, з відступом | вичерпавши спроби — наступна сходинка; модель — у штрафний ящик |
| `401/403` | ні | наступна модель не полагодить ключ до шлюзу |

Таймаут **свій на модель** (`timeout_ms` у реєстрі), а не один на всіх:
`@exo/kit/llm` зашив 30 с для будь-чого, і роздум `claude-opus-4-6-thinking`
через це невідрізненний від мертвого `flash-lite`.

`Retry-After` поважається, якщо є. Станом на 2026-09-13 шлюз його **не шле** —
перевірено прямим `curl -D -`; доти діє власне охолодження.

## Здоров'я: пул, модель, вхід — три різні питання

| що | питання | ознака | наслідок |
|---|---|---|---|
| **пул** | чи пускає метр | `429` | пул `exhausted` на охолодження, драбина його пропускає |
| **модель** | чи жива саме ця модель | `5xx`, `400`, надгробок, **таймаут** | штрафний ящик моделі; пул лишається `unknown` — придатним |
| **вхід апстріму** | чи є в шлюзу вхід узагалі | `500 auth_unavailable`, `401/403`, `400 unknown provider for model` — у **кількох** пулах | `checks.upstream = expired` → `/health/ready` **503** |
| **шлюз** | чи до нього взагалі дійти | відмова з'єднання, DNS, скидання | пул `down`, `checks.upstream = down` → 503 |

`/health/ready` віддає `checks.upstream` (`ok` / `expired` / `down` /
`unknown`) і поле `upstream.detail` з причиною. `expired` — коли відмову входу
бачать щонайменше два пули і відтоді не було жодної справжньої відповіді: одна
модель з `auth_unavailable` серед живих сусідів — штраф моделі, так уже було
тричі. `429` — не вирок, а доказ, що вхід живий. `unknown` — лише до першої
відповіді після старту.

**Таймаут — не «шлюз лежить».** Недосяжний шлюз — це з'єднання, якого не
вийшло; таймаут — з'єднання було, моделі забракло часу. Доти обидва читались
як «шлюз недосяжний», і одна повільна проба клала весь пул у `down`.

## Стелі

Дві: на **продукт** (нова) і на **кінцевого клієнта** (спадкоємець двох копій
`spend.ts` з exointel і teamself). Властивості перенесені свідомо: `INCR` +
`EXPIRE NX`, TTL 48 год, день у **UTC**, лічильник **перед** викликом, і
**fail-open** — недоступний Redis не має гасити підтримку. Перевищення
деградує в **передачу людині**, а не в 402.

## Облік і журнал

Таблиця `ai_call` у спільному Postgres (база `blackgate`), міграції — dbmate —
рядок на **спробу** драбини. З 2026-09-25 поруч `ai_request` — рядок на
**кожен** `/v1/complete`, і відмову теж (400, 401, 429 стелі, 503): статус,
модель, сума токенів, латентність, трейс і — за налаштуванням — **вміст**
(повідомлення й відповідь). Спроби посилаються на свій запит (`request_ref`).
Запис після відповіді, не тримає її. Строк: вміст 90 днів (стає `NULL`),
рядок 365 (`JOURNAL_*` у `.env`, перекриваються в панелі).
`cost_usd` лишається `NULL`, поки в реєстрі немає `price_*_per_mtok`:
**вигадана цифра гірша за порожню**, бо за нею ухвалювали б рішення. Токени
шлюз віддає — перевірено на всіх чотирьох пулах.

## Заглушка замість моделей

Фальшивий **апстрім**, а не фальшивий сервіс: підмінюється лише транспорт до
моделей. Ключ продукту, стелі, драбина з ретраями, коди відповіді й рядки в
`ai_call` лишаються справжніми. Заглушка йде крізь ту саму драбину, що й
моделі: два фальшиві пули `stub-a`/`stub-b` з моделями `stub-primary` і
`stub-fallback`.

Вмикається **лише** записом у `config/stub.yaml` (та сама тека, що й реєстр,
перечитується за mtime). Файла немає — вимкнено для всіх. Автоматично для всіх
не вмикається ніколи: клієнт, що отримав би підробку замість чесного
fail-safe, — рівно той дефект, від якого сервіс писався.

```yaml
version: 1
routes:                       # перший, що підійшов
  - { product: exopost, mode: always }                  # моделі не питаються
  - { product: teamself, subject: sandbox, mode: always }
  - { product: exointel, subject: "exointel:user:42", mode: fallback }  # лише після 503
responses:                    # перша, що підійшла; інакше JSON зі схеми, інакше текст
  - { product: exopost, subject: "exopost:stage:classify", schema: ClassifyResult, content: '{…}' }
```

`subject` — точно або префіксом із `*`; без `subject` — увесь продукт, і без
гаманця теж. `schema` — `title` JSON Schema у промпті (ім'я pydantic-моделі).

**Відповідь.** Завжди видно, що це заглушка: `stub: true` у тілі, `model` і
`pool` — `stub-*`, текст починається з `[stub]`. Структурована стадія, що кладе
JSON Schema в системний промпт (так робить exopost), отримує найменший
екземпляр цієї схеми: `enum` — перше значення, числа — нижня межа, рядки —
`[stub] <поле>`. Валідаторів поверх схеми звідси не видно, тож для таких стадій
є `responses`. Токени — `null`: заглушка нічого не спалила. У `ai_call` її
рядки відрізняє `pool LIKE 'stub-%'`.

**`fallback`** — справжня драбина йде першою; заглушка відповідає лише на її
503, а справжні спроби лишаються в `attempts` і в обліку, заглушка — номерами
сходинок після них.

**Сценарії** — мітка в тексті повідомлення, лише в режимі `always` (в
`fallback` це просто текст для моделі). Невідома мітка — 400, щоб тест із
друкарською помилкою не зеленів.

| мітка | що робить `stub-primary` | що бачить продукт |
|---|---|---|
| `[stub:429]` | 429, пул вичерпаний | відповідь з `rung: 1` |
| `[stub:500]` | 5xx, ретраї з відступом | `rung: 1`, `tries: 3` |
| `[stub:slow]` | таймаут моделі (1 с), ретраї | `rung: 1` за ~4,5 с |
| `[stub:retired]` | підроблений 200 | `rung: 1` |
| `[stub:rejected]` | 400 на форму | `rung: 1` без ретраїв |
| `[stub:empty]` | 200 з порожнім текстом | `content: null` |
| `[stub:all-fail]` | обидві сходинки 5xx | 503 `all_rungs_failed` |
| `[stub:budget]` | моделі не питаються | 429 `budget_exhausted`, лічильник не чіпається |

Стан пулів заглушки свій на кожен запит: `[stub:429]` не кладе `stub-a`
наступним запитам.

## Панель

Окремий слухач на **3001** (`ADMIN_PORT`): `/admin/api/*` і SPA з `web/`
(Vite + React 19 + `@exo/kit-ui`, графіки uPlot). Порт 3000 (`/v1`) без змін.
Без `ADMIN_HTPASSWD` (htpasswd, apr1 або bcrypt) слухач не піднімається;
Basic перевіряється в застосунку, хоч би що стояло перед ним, а зміни —
лише з `X-Requested-With: blackgate-panel` і Origin свого хоста.

Налаштування (стелі — спільні й на продукт; журнал) лежать перекриттям у
таблиці `setting` поверх `.env`. Кожна зміна налаштувань, реєстру чи заглушки
з панелі — рядок `config_change` (хто, коли, до/після, різниця) з відкатом.

| змінна | дефолт | що |
|---|---|---|
| `ADMIN_PORT` | 3001 | слухач панелі |
| `ADMIN_HTPASSWD` | — | `user:hash` через кому; порожньо — панелі немає |
| `ADMIN_WEB_ROOT` | `/app/web` | зібрана SPA |
| `JOURNAL_STORE_CONTENT` | `true` | писати вміст запитів |
| `JOURNAL_CONTENT_DAYS` / `JOURNAL_RETENTION_DAYS` | 90 / 365 | строки вмісту й рядка (0 — без строку) |
| `UPSTREAM_MANAGEMENT_KEY` | — | ключ Management API двигуна під VibeConduit (лише читання акаунтів) |
| `UPSTREAM_PANEL_URL` | — | посилання на його Management Center |
| `OTEL_EXPORTER_OTLP_ENDPOINT` | — | приймач OTLP/HTTP; порожньо — експорт вимкнений |
| `OTEL_EXPORTER_OTLP_HEADERS` | — | `k=v,k2=v2` |
| `OTEL_INSTRUMENTATION_GENAI_CAPTURE_MESSAGE_CONTENT` | `false` | вміст у спанах (`gen_ai.input/output.messages`) |


## Що лишилось від старої назви — свідомо

Перейменування доведене до споживачів того ж дня: Python-пакет тепер
`blackgate-client` (модуль `blackgate_client`, клас `Blackgate`), змінні —
`BLACKGATE_URL`/`BLACKGATE_KEY` (exointel, teamself) і
`EXOPOST_BLACKGATE_URL`/`EXOPOST_BLACKGATE_KEY` (exopost). Лишилось:

* **Префікс виданих ключів продуктів** `exoai-<продукт>-…` — секрети в `.env`
  чотирьох продуктів; ключ лише називає продукт, префікс нічого не значить.
* **Коментар-шапка `catalog.yaml`** — реєстр моделей правиться окремо від
  перейменування.
* **Історія**: `generation.provider = 'ExoAIProvider'` у старих рядках exopost,
  записи CHANGELOG і журналів до 2026-09-24.
