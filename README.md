# exo-ai

Шлюз до моделей: **пули**, **драбина запасних ходів**, **облік**.

Стоїть *перед* VibeConduit, а не замість нього. Шлюз лишається виходом до
провайдерів (там живе автентифікація до Google і Vertex), exo-ai бере політику,
якої в шлюзі немає взагалі: мапінгу моделей, обліку, ретраїв, лімітів і поняття
пулу в ньому нема.

    продукт ──(тир, ключ продукту)──▶ exo-ai ──(id моделі)──▶ VibeConduit ──▶ провайдер

## Навіщо

2026-09-13 пул Gemini 3.x ліг цілком. Запасна модель teamself лежала **в тому
самому пулі**, що й основна, — уся драбина пішла у fail-safe за один крок.
Відповідав лише exointel, чия запасна модель випадково була з іншого пулу.

Сервіс прибирає клас хвороби, а не рядок у `.env`:

* **пул — це те, що вичерпується разом.** Не сімейство назв і не версія.
* **драбина мусить перетинати пули.** Конфіг, де сусідні сходинки в одному
  пулі, сервіс **не приймає на старті** і називає обидві сходинки.
* **здоров'я пулів — наперед.** Відомо мертвий пул драбина пропускає, а не
  з'ясовує це запитом клієнта.
* **облік.** Кожен виклик лишає рядок: продукт, модель, пул, сходинка,
  результат, латентність, токени.

## API

Продукт просить **тир**, а не модель. `fast` / `capable` / `agent` — саме те,
чим сьогодні думають exointel і teamself; id моделі стає деталлю сервісу.

```http
POST /v1/complete
Authorization: Bearer <ключ продукту>

{ "tier": "fast", "messages": [{"role":"user","content":"…"}],
  "max_tokens": 512, "temperature": 0.3, "subject": "user:42" }
```

```json
{ "content": "…", "model": "gemini-2.5-flash", "pool": "gemini-lite",
  "rung": 1, "attempts": [ … ], "totalLatencyMs": 812 }
```

`rung: 1` і масив `attempts` віддаються навмисно: продукт має бачити, що
відповіла не основна модель, — інакше деградація знову стає невидимою.

| код | що це | що робити продуктові |
|---|---|---|
| 200 | відповідь є | брати `content` |
| 429 `budget_exhausted` | добова стеля | **передати людині**, не показувати помилку і не виставляти рахунок |
| 503 `all_rungs_failed` | жодна сходинка не відповіла | fail-safe продукту |
| 400 `unknown_tier` | тиру немає в реєстрі | помилка інтеграції |

Решта: `GET /v1/pools` (стан пулів), `GET /v1/tiers` (розгорнуті драбини),
`GET /v1/usage` (скільки цей продукт спалив сьогодні), `/health/live`,
`/health/ready` (обидва без ключа).

Клієнти: TypeScript — `@exo/kit/ai` у [exo-kit](https://github.com/eXocriador/exo-kit);
Python — [`clients/python`](clients/python/README.md) у цьому репо (async `httpx`,
типізовані помилки на кожен рядок таблиці вище).

## Реєстр моделей — дані, не код

`catalog.yaml` монтується з теки продукту `:ro` і перечитується за mtime
(15 с). Додати модель, пул чи сходинку драбини — правка файла, **без релізу**.
Поганий реєстр на старті валить процес; поганий реєстр на перечитуванні
**відхиляється, а в роботі лишається попередній** — живий сервіс не має лягати
від того, що хтось зберіг файл посеред правки.

Розкладка пулів знята **живою пробою**, а не вгадана з імен. Проба спростувала
очевидне: `gemini-3.1-pro-low` віддавав 429, а `gemini-3.1-flash-lite` — 200.
Один префікс версії, різні пули.

**Якщо сумніваєшся — зливай пули, не розділяй.** Зайво зліплені два пули лише
звужують драбину. Помилково розділений один пул — це рівно той дефект, від
якого сервіс і написаний.

## Підроблений 200

Три моделі (`gemini-3.5-flash-low`, `gemini-3.5-flash-extra-low`,
`gemini-3-flash-agent`) виведені апстрімом з експлуатації, але шлюз віддає на
них **HTTP 200** — з `model: "model"`, `usage: null` і текстом «Gemini 3.5 Flash
is no longer available…» замість відповіді.

Наслідки без захисту тихі обидва: монітор за кодом статусу назве пул здоровим,
а продукт покаже цей текст користувачеві **як відповідь моделі**. Тому:
позначка `retired:` закриває три відомі id (сервіс не пускає їх ні в драбину,
ні в пробу пулу), а структурний детектор у `src/upstream/gateway.ts` ловить
четвертий, якого ще ніхто не бачив.

## Коди і ретраї — в одному місці

| код | ретрай | далі |
|---|---|---|
| `429` | ні | пул позначається хворим, наступна сходинка (з іншого пулу) |
| `400 INVALID_ARGUMENT` | **ні** | записати, що модель у цій формі не працює, і йти далі |
| `5xx`, таймаут | так, з відступом | вичерпавши спроби — наступна сходинка |
| `401/403` | ні | наступна модель не полагодить ключ до шлюзу |

Таймаут **свій на модель** (`timeout_ms` у реєстрі), а не один на всіх:
`@exo/kit/llm` зашив 30 с для будь-чого, і роздум `claude-opus-4-6-thinking`
через це невідрізненний від мертвого `flash-lite`.

`Retry-After` поважається, якщо є. Станом на 2026-09-13 шлюз його **не шле** —
перевірено прямим `curl -D -`; доти діє власне охолодження.

## Стелі

Дві: на **продукт** (нова) і на **кінцевого клієнта** (спадкоємець двох копій
`spend.ts` з exointel і teamself). Властивості перенесені свідомо: `INCR` +
`EXPIRE NX`, TTL 48 год, день у **UTC**, лічильник **перед** викликом, і
**fail-open** — недоступний Redis не має гасити підтримку. Перевищення
деградує в **передачу людині**, а не в 402.

## Облік

Таблиця `ai_call` у спільному Postgres (`exo_ai`), міграції — dbmate.
`cost_usd` лишається `NULL`, поки в реєстрі немає `price_*_per_mtok`:
**вигадана цифра гірша за порожню**, бо за нею ухвалювали б рішення. Токени
шлюз віддає — перевірено на всіх чотирьох пулах.
